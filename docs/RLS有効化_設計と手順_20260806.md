# RLS有効化 設計と手順（2026-08-06 調査）

RLS＝データベースが「この行を、この人に見せてよいか」を1行ごとに判定する仕組み。
いまは無効なので、**公開されているanon鍵さえあれば誰でも全データを読める**。

---

## 0. 結論（先に読む）

**`005_rls_store_isolation.sql` をそのまま適用してはいけない。KYOUKANOが全画面真っ白になる。**

005はこう書かれている：

> anon（PINログインアプリ）→ `store_id IS NULL` のデータのみアクセス可

これは「KYOUKANOのデータには店舗IDが入っていない」という前提。
**実際のKYOUKANOのデータには `store_id = 4cb3383a-…` が入っている**（[[kyoukano-store-id-not-null]]）。
前提が後から崩れたまま放置されている。

---

## 1. いま分かっている良い材料

`pin-login` Edge Function は既に**本物の認証セッションを発行**し、
`store_members` に「この人はこの店舗」の紐づけを必ず作る（`pin-login/index.ts:545-556`）。

→ ログイン後のユーザーは `authenticated` なので、
   `store_id = get_my_store_id()` という素直なポリシー1本で全テーブルを守れる。
   **anon向けの特別扱いはログイン後には要らない。**

---

## 2. 🚨 そのままでは壊れる箇所（ログイン前にanon鍵で直接テーブルを読んでいる）

| 関数 | 行 | 読んでいるもの |
|---|---|---|
| `loadStoreDataForPin` | 3561-3564 | courses / options / rooms / store_settings |
| `init` | 4247-4279 | casts / courses / options / store_settings / rooms |
| `autoOwnerPasskeyLogin` | 4107 | passkeys (cast_id=0) |
| `ownerPasskeyLogin` | 4132 | passkeys (cast_id=0) |
| `doOwnerLoginSmart` | 4454 | passkeys (cast_id=0) |
| `autoPasskeyLogin` | 4320,4332 | passkeys / casts |
| `passkeyLogin` | 4352,4368 | passkeys / casts |
| `doCastLoginSmart` | 4489,4501 | passkeys / casts |
| `doCastLogin` | 4596,4614 | casts |

**RLSを入れると、これらが全部0件を返す＝ログイン画面から先へ進めなくなる。**

---

## 3. 🚨 調査中に見つかった、今すでに存在する情報漏れ

RLSが無いため、**anon鍵だけで次が読める**（アプリを経由しなくても、URLを叩くだけで）。

| 読めるもの | 中身 |
|---|---|
| `casts` 全列 | **PINが平文**（[[setpin-plaintext-tradeoff]] で意図的にそうしている） |
| `store_settings` 全列 | `owner_pin` |
| `customers` / `reservations` | 顧客の氏名・電話・来店履歴 |

anon鍵は `index.html` に書いてあるので、**実質公開情報**。
※ログインには端末トークンも要るので「PINを知る＝即入店」ではないが、
　顧客の個人情報が読める状態そのものが問題。

---

## 4. 進め方（2段階。1段目は営業中でも安全）

### Phase A: ログイン前の読み取りをEdge Functionへ移す（見た目の変化なし）
新しい Edge Function `login-bootstrap` を作り、**端末トークンと引き換えに**
ログイン画面が必要とする最小限だけを返す（service_role で動くのでRLSを通り抜ける）。

返すもの（これ以上は返さない）:
- `casts`: `id, name, active, sort_order`（**pin は返さない**）
- `courses` / `options` / `rooms`: 表示に要る列のみ
- `store_settings`: 表示に要る列のみ（**owner_pin は返さない**）
- `passkeys`: 認証に要る列のみ

→ フロントの上記10箇所をこの関数の呼び出しに差し替える。
   **この時点ではRLSはまだ無効なので、失敗しても画面は壊れない。**

### Phase B: RLSを有効化（深夜作業）
005を書き直して適用する。方針:

```sql
-- anon には一切許可しない（ログイン前の読み取りはPhase Aで無くなっている）
-- authenticated は自分の店舗のみ
using (store_id = get_my_store_id())
```

`store_id IS NULL` の行（もし残っていれば）は誰からも見えなくなるので、
**適用前に「store_id が NULL の行が本当に0件か」を必ず数える。**

---

## 5. 切り戻し

RLSは1テーブルずつ即座に無効化できる。

```sql
alter table casts disable row level security;
-- 以下、対象テーブル分
```

**Phase B の作業前に、この無効化SQLを全テーブル分そのまま貼れる形で用意しておくこと。**
深夜に慌てて書かない。

---

## 6. 事前に取るべき情報（読み取りのみ・営業中でも安全）

```sql
-- ① いまRLSが有効なテーブルはどれか
select relname, relrowsecurity
from pg_class where relnamespace='public'::regnamespace and relkind='r'
order by relrowsecurity desc, relname;

-- ② store_id が NULL の行が残っていないか（残っていると見えなくなる）
select 'casts' t, count(*) from casts where store_id is null
union all select 'reservations', count(*) from reservations where store_id is null
union all select 'customers', count(*) from customers where store_id is null
union all select 'works', count(*) from works where store_id is null
union all select 'shifts', count(*) from shifts where store_id is null
union all select 'courses', count(*) from courses where store_id is null
union all select 'options', count(*) from options where store_id is null
union all select 'rooms', count(*) from rooms where store_id is null
union all select 'store_settings', count(*) from store_settings where store_id is null
union all select 'cast_fees', count(*) from cast_fees where store_id is null
union all select 'passkeys', count(*) from passkeys where store_id is null;
```

②で1件でも出たら、**その行はRLS適用後に誰からも見えなくなる**。
先に `store_id` を埋めるか、意図的に捨てるかを決める（[[feedback_backfill_client_isnull]]）。
