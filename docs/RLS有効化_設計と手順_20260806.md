## 2. ~~🚨 穴① customer_memos が完全に素通し~~ → ✅ **解消済み（2026-08-07 0:53 実測）**

> **本番で確認した結果、この穴は既に塞がっていた。**
> - `SELECT policyname FROM pg_policies WHERE tablename='customer_memos'` → **0行**
> - `SELECT relrowsecurity FROM pg_class WHERE relname='customer_memos'` → **true**
>
> RLS有効＋ポリシー0本＝**誰も読み書きできない**。`032_lock_customer_memos.sql` は適用済み。
>
> ⚠️ **判定にはこの2つを必ずセットで見ること。** ポリシー0行だけでは安全と言えない
> （RLS無効＋ポリシー0本なら**誰でも全件読める**という正反対の状態になる）。
> また `customer_memos` は0行のテーブルなので、anon鍵でcurlしても
> どちらの状態でも `[]` が返り**区別できない**。

<details><summary>当時の記録（発見時の状況）</summary>

```
allow_all_customer_memos   roles={anon}    cmd=ALL     using=true
read memos                 roles={public}  SELECT      using=true
update memos               roles={public}  UPDATE      using=true
delete memos               roles={public}  DELETE      using=true
```

**公開鍵さえあれば誰でも全件を読み書き削除できる。**

経緯は `008_drop_legacy_policies.sql:14` に書かれている：

> customer_memos: shop_idカラムのため対象外（既存ポリシーを維持）

`store_id` ではなく `shop_id` を持つ旧設計のテーブルで、一括整理から外れたまま
緩いポリシーだけが残った。

**現状は無害**（行数0・アプリからの参照0）。**ただし使い始めた瞬間に顧客メモが全公開になる。**

→ 修正: `032_lock_customer_memos.sql`（ポリシーを全削除。RLS有効＋ポリシー0本＝誰も触れない）

</details>

## 3. ~~⚠️ 穴② homepage_shifts の書き込みが店舗をまたげる~~ → ✅ **対応完了（2026-08-07 1:11）**

> **`033_lock_homepage_shifts_write.sql` を本番に適用済み。**
> `store_id` 列が無いテーブルなので、**`cast_id → casts.store_id` を辿って店舗を判定**する
> ポリシーにした（列は一切変更していない＝外部の同期システムの形式に手を触れていない）。
>
> **適用を安全と判断した根拠（適用前に実測）**:
> - 最終 `created_at`/`updated_at` = **2026-05-25** ＝ 外部の同期は2ヶ月半停止していた
> - `cast_id` が `casts` に無い「迷子の行」= **0件**（`FOR ALL` の `USING` はDELETEにも効くため、
>   迷子があると `deleteCast` の後始末が失敗する）
> - `casts.store_id` が NULL の行 = **0件**（NULLだと誰も書けなくなる）
>
> **適用後の検証**: 匿名の読み取り=45件で従来どおり（ホームページの表示は無事）／
> 匿名の書き込み=`42501` で拒否。
>
> ⚠️ **1〜2日のうちにホームページのシフトが更新されなくなったら、まずこれを疑って戻すこと**
> （ロールバックSQLは033のファイル末尾に記載）。外部システムの書き込み経路だけは
> 向こうが動くタイミングでしか確認できない。

<details><summary>当時の記録（発見時の状況）</summary>

```
homepage_shifts_read    roles={anon,authenticated}  SELECT  using=true
homepage_shifts_write   roles={authenticated}       ALL     using=true
```

読みが公開なのはホームページ表示用なので意図どおり。
問題は**書き込み**で、**ログインさえしていれば、どの店舗のデータでも書き換えられる。**

- **いまは1店舗なので実害なし。**
- **2店舗目が入った瞬間に、他店のホームページ用シフトを書き換えられる状態になる。**

⚠️ このテーブルは `supabase/migrations/` に無く、アプリからは
`deleteCast` の後始末で DELETE しているだけ（`index.html:10934`）。
**外部のホームページ側システムが書き込んでいる可能性が高い**ので、
うかつに絞ると外部側が壊れる。**書いている主体を特定してから直すこと。**

→ **2店舗目の契約前に必ず対応。** [[trigger-enable-rls-on-new-store]]

</details>

```bash
K=$(grep -m1 -oE "eyJ[A-Za-z0-9_.-]{100,}" index.html)
curl -s "$U/rest/v1/customers?select=id&limit=1" -H "apikey: $K" -H "Authorization: Bearer $K"
```

`[]` が返れば守られている。`id` だけを要求するので個人情報には触れない。
