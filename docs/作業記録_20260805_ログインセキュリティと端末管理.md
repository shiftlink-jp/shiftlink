# 作業記録 2026-08-05｜ログインセキュリティと端末管理

きっかけ：管理画面の「登録済みの端末」が26台／12名分になり、うち20台が
「誰のPINでもログインできます」と表示されていた。これは何なのか、という確認から始まった。

## 1. 結論（先に読むところ）

- **同僚が他人のPINを見られる穴を塞いだ**（当初いちばん直したかった問題）
- **退店処理を押せば、ログイン手段が全部止まるようになった**（端末・生体認証・PIN・ログイン中のセッション）
- **端末の一覧を普段の画面から畳んだ**（26台の羅列と赤い警告が出なくなった）
- 端末の仕組み自体は「未完成」と記録されていたが、**実際にはとっくに完成して本番稼働していた**

すべて本番反映済み。アプリの見た目・動きは、上記以外は変わっていない。

### ④ 同僚なりすましの穴を塞いだ（027適用）

`casts.pin` に平文PINが11件残っており、ログインしたセラピストが同僚全員のPINを読めた。

オーナー画面のPINバッジは従来どおり表示される（確認済み）。

### ⑤ 退店処理でログイン手段を一括失効（新規実装・本番反映済み）

**これまで**：退店処理は割引設定・ホームページシフト・セラピスト本体を消すだけで、
端末登録・生体認証・金庫のPIN・ログイン中のセッションが残っていた（監査の「失効漏れ」指摘に該当）。

**これから**：`manage-devices` に `action=offboard_cast` を追加し、`deleteCast` が
casts を消す**前**に呼ぶ。失敗したら退店処理ごと中止する（消したつもりで入れたまま、を防ぐ）。

| 対象 | 処理 |
|---|---|
| 端末 | 本人に紐づいた端末を失効。紐づいていない端末は**氏名が店内で一意のときだけ**ラベル照合 |
| 生体認証 | `passkeys` を store_id + cast_id で削除 |
| 金庫のPIN | `auth_pins` の `cast.<id>` を削除 |
| ログイン中のセッション | `store_members` 削除＋Authユーザーごと削除＝**即時無効化** |

**売上・シフト・委託金・予約には一切触らない**（税務・帳簿用に保持）。

### ⑥ 過去の残骸を掃除

すでに存在しないセラピストの `auth_pins` 14件・`passkeys` 12件が残っていた（今日の修正より前の退店分）。
SQLで削除し、両方0を確認。
※危険ではなかった：PINは `active=true` の人しか照合されず、生体認証も署名検証の前に
在籍確認して拒否する作りになっている。

### ⑦ 端末一覧を既定で畳んだ（本番反映済み）

「登録済みの端末」を開閉式にし、初期表示は閉じる。開いたときに初めて読み込む。
26台の羅列と「うち20台は本人紐づけがありません」の赤い警告が、普段は出なくなった。
紛失時に1台だけ解除する用途のため機能は残す。
説明文も「退職時は手動で解除してください」→「退店処理をすれば自動で解除されます」に修正。

## 3. 検証の状況（正直な記録）

| 項目 | 状態 |
|---|---|
| PIN平文のクリアと、その後のPINバッジ表示 | ✅ 実機確認済み |
| 退店処理の一連の流れ（確認画面→完了メッセージ→一覧から消える） | ✅ 実機確認済み（テスト用セラピスト2名） |
| 生体認証・PIN・セッションの失効 | ✅ 処理が通ることを確認 |
| **端末の解除** | ❌ **未実証**。テスト2回とも「端末0台」だった |
| 端末一覧の畳み込み | ✅ 本番配信を確認 |

**「端末0台」の理由**：テスト用セラピストが、すでに「オーナー」名義で登録済みの端末
（今野さんのMac）からログインしたため、その人名義の端末が存在しなかった。
プログラムは正しく動いている。真の検証にはプライベートウィンドウ等
「まっさらな端末」からログインする必要がある。

**ここで判明した設計上の弱点**：自動登録は初回だけ名前ラベルを付け、以後**上書きしない**。
そのため1台を複数人が使うと最初の人の名前のままになる。
一覧に並んでいた「MacBook」「SHIFT LINK」「澤木」といった謎のラベルも同じ原因。

## 5. 検討したが見送ったこと

**長いログインID＋PIN方式への切り替え**（端末登録を丸ごと廃止する案）。

業界調査の結果、Square・Toastは端末を登録するが**店の備品が数台だから成立**しており、
RESERVA・サロンボード等のサロン予約系は端末を登録しない。ShiftLinkは
**私物スマホに共有端末型の仕組みを当てている**ため、台数が人数を超えて増える構造だった。

ただし端末ペアリングは既に完成しており、乗り換えると同じ問題を別方式で解き直す二度手間になる。
まず既存を完成させ、それでも管理が煩わしければ改めて検討する、という判断。

調査結果：`マーケ部/成果物/リサーチ_ログイン端末管理_業界標準_20260805.md`

## 5-2. 支払い方法をカード → 銀行振込へ（**本番未反映・Stripe承認待ち**）

判断理由：**手数料**。月額14,800円（税込16,280円）に対し

| 方法 | 料率 | 1店舗あたり月 | 10店舗で年間 |
|---|---|---|---|
| Stripeカード（現行） | 3.6% | 586円 | 70,300円 |
| Stripe銀行振込 | **1.5%** | **244円** | 29,300円 |
| 直接振込（Stripeなし） | 0% | 0円 | 0円 |

「直接振込」は手数料ゼロだが、入金確認・督促・利用停止がすべて手作業になり、
**止め忘れの取りこぼし（月16,280円）が手数料（586円）を上回る**ため不採用。
Stripeの銀行振込なら仮想口座への入金が自動で消し込まれ、自動化を保ったまま料率が半分以下になる。

### 決めたこと
- **銀行振込のみ**（カードは廃止。コードはコメントで温存し、戻せるようにした）
- **支払期限：請求書の発行から7日**
- **申し込み直後から利用可**（前払いにすると成約率が落ちるため）。未入金は期限超過で自動停止

### 実装済み（staging まで。main には出していない）
`supabase/functions/stripe-checkout/index.ts`
- Checkout Session(mode=subscription) を廃し、`subscriptions.create` に変更
  - `collection_method: 'send_invoice'` / `days_until_due: 7`
  - `payment_settings.payment_method_types: ['customer_balance']`
  - `payment_method_options.customer_balance.bank_transfer.type: 'jp_bank_transfer'`
- 請求書が `draft` のままだと振込先が発行されないため、その場で `finalizeInvoice` して
  `hosted_invoice_url` を返す
- **二重契約の防止**：生きている契約（active/trialing/past_due/unpaid/incomplete）があれば
  新規作成せず既存の請求書URLを返す（ボタン連打での二重請求を防ぐ）

`index.html`：アップグレード画面の文言とボタンを銀行振込に変更（SW_VER v61）
`tokutei.html`：支払い方法・支払い時期・提供時期の記載を銀行振込に更新

### アプリ側の課金判定は変更不要
`stores.subscription_status` を見る1箇所（index.html:4878）だけで制御しており、
Stripeがその値を書き換える構造は同じ。webhook も `invoice.paid` /
`invoice.payment_failed` を既に処理しているため、追加実装は不要だった。

### ⛔ ブロック中：Stripeの審査
2026-08-05時点、Stripeダッシュボードの「銀行振込」は **承認待ち**。
承認が下りるまで本番反映してはいけない（申し込みボタンがエラーになる）。
**本番は現在もカード決済のまま正常稼働している。**

### 承認後にやること
1. 設定 > 請求 > 請求書 で「銀行振込」をデフォルトの決済手段にする
2. 同ページ「調整と照合」で以下をON
   - **部分銀行振込による決済を自動的に照合する**
   - **請求書を自動的に書き消す**（振込手数料を引かれて数百円不足する事故の自動処理）
3. `stripe-checkout` を本番デプロイ＋アプリ(v61)を main へ
4. 自分で申し込んでみて、振込先が表示されるか確認

### 覚えておくこと
- **銀行振込は自動引き落としではない。** 毎月、店舗が自分で振り込む。払い忘れは必ず起きる
- Stripeの表示上、**入金の確定に0〜3営業日**かかる。期限ギリギリの振込は着金が期限を過ぎうる
- 振込手数料は店舗負担（当方の取り分は減らない）
