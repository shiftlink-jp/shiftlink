# 作業記録 2026-08-05｜ログインセキュリティと端末管理

きっかけ：管理画面の「登録済みの端末」が26台／12名分になり、うち20台が
「誰のPINでもログインできます」と表示されていた。これは何なのか、という確認から始まった。

---

## 1. 結論（先に読むところ）

- **同僚が他人のPINを見られる穴を塞いだ**（当初いちばん直したかった問題）
- **退店処理を押せば、ログイン手段が全部止まるようになった**（端末・生体認証・PIN・ログイン中のセッション）
- **端末の一覧を普段の画面から畳んだ**（26台の羅列と赤い警告が出なくなった）
- 端末の仕組み自体は「未完成」と記録されていたが、**実際にはとっくに完成して本番稼働していた**

すべて本番反映済み。アプリの見た目・動きは、上記以外は変わっていない。

---

## 2. やったこと

### ① 作業場（staging）の立て直し ★事故を1つ未然に防いだ

`staging` ブランチが3か月前で止まっており、**アプリ本体のファイルが存在しなかった**。
さらに7月の作業で「`index.html` を倉庫にしまう」という指示が残っていて、当時は
ルートの `index.html` が旧LPだったので正しかったが、**現在は同じ名前がアプリ本体**。
そのまま本番に反映すると**アプリが消える**状態だった（過去に一度起きた事故と同じ形）。

対応：本番と同じ内容で作り直し、価値のある手順書3本だけを載せ替え。
危険な整理コミット2件は取り込まず。旧ブランチは `backup/staging-20260805` に保管。

### ② 未使用の旧素材47件を退避（本番反映済み）

ルートの `images/`(45件) と `videos/`(2件) はどこからも参照されていない旧素材だった。
公開中のLPは `lp/images` `lp/videos` の新版を使用。`_archive/lp-画像素材_未使用_20260805/` へ移動。
中身の変更はゼロ（全件が「移動しただけ」）。

※副作用：`https://shiftlink-app.jp/images/～` という直リンクは404になった。現行LPは影響なし。

### ③ 記録と現実のズレを解消

記録では「端末ペアリング改修は既存関数3本の差し替えが未実施」となっていたが、
本番Supabaseを見たところ **6つの関数すべてが8/2〜8/3に差し替え済み**だった。
アプリも v58 が本番稼働中で、リポジトリと1バイト差なし。**記録の方が古かった。**

### ④ 同僚なりすましの穴を塞いだ（027適用）

`casts.pin` に平文PINが11件残っており、ログインしたセラピストが同僚全員のPINを読めた。
本番SQLで NULL 化（実行前11件 → 実行後0件）。
PIN自体は金庫（`auth_pins.pin_plain`／サーバーからしか触れない）に残り、
オーナー画面のPINバッジは従来どおり表示される（確認済み）。

### ⑤ 退店処理でログイン手段を一括失効（新規実装・本番反映済み）

**これまで**：退店処理は割引設定・ホームページシフト・セラピスト本体を消すだけで、
端末登録・生体認証・金庫のPIN・ログイン中のセッションが残っていた（監査の「失効漏れ」指摘に該当）。

**これから**：`manage-devices` に `action=offboard_cast` を追加し、`deleteCast` が
casts を消す**前**に呼ぶ。失敗したら退店処理ごと中止する（消したつもりで入れたまま、を防ぐ）。

| 対象 | 処理 |
|---|---|
| 端末 | 本人に紐づいた端末を失効。紐づいていない端末は**氏名が店内で一意のときだけ**ラベル照合 |
| 生体認証 | `passkeys` を store_id + cast_id で削除 |
| 金庫のPIN | `auth_pins` の `cast.<id>` を削除 |
| ログイン中のセッション | `store_members` 削除＋Authユーザーごと削除＝**即時無効化** |

**売上・シフト・委託金・予約には一切触らない**（税務・帳簿用に保持）。

### ⑥ 過去の残骸を掃除

すでに存在しないセラピストの `auth_pins` 14件・`passkeys` 12件が残っていた（今日の修正より前の退店分）。
SQLで削除し、両方0を確認。
※危険ではなかった：PINは `active=true` の人しか照合されず、生体認証も署名検証の前に
在籍確認して拒否する作りになっている。

### ⑦ 端末一覧を既定で畳んだ（本番反映済み）

「登録済みの端末」を開閉式にし、初期表示は閉じる。開いたときに初めて読み込む。
26台の羅列と「うち20台は本人紐づけがありません」の赤い警告が、普段は出なくなった。
紛失時に1台だけ解除する用途のため機能は残す。
説明文も「退職時は手動で解除してください」→「退店処理をすれば自動で解除されます」に修正。

## 3. 検証の状況（正直な記録）

| 項目 | 状態 |
|---|---|
| PIN平文のクリアと、その後のPINバッジ表示 | ✅ 実機確認済み |
| 退店処理の一連の流れ（確認画面→完了メッセージ→一覧から消える） | ✅ 実機確認済み（テスト用セラピスト2名） |
| 生体認証・PIN・セッションの失効 | ✅ 処理が通ることを確認 |
| **端末の解除** | ❌ **未実証**。テスト2回とも「端末0台」だった |
| 端末一覧の畳み込み | ✅ 本番配信を確認 |

**「端末0台」の理由**：テスト用セラピストが、すでに「オーナー」名義で登録済みの端末
（今野さんのMac）からログインしたため、その人名義の端末が存在しなかった。
プログラムは正しく動いている。真の検証にはプライベートウィンドウ等
「まっさらな端末」からログインする必要がある。

**ここで判明した設計上の弱点**：自動登録は初回だけ名前ラベルを付け、以後**上書きしない**。
そのため1台を複数人が使うと最初の人の名前のままになる。
一覧に並んでいた「MacBook」「SHIFT LINK」「澤木」といった謎のラベルも同じ原因。

## 4. 残っている宿題

| | 内容 | 優先度 |
|---|---|---|
| ⬜ | **端末を本人に自動で紐づける**（初回ログイン時に `bound_cast_id` を付ける）。既存20台のラベル照合による一括紐づけは、同名や改名で誤爆すると本人が締め出されるため、対応表を確認してから | 中 |
| ⬜ | 端末解除の実証テスト（プライベートウィンドウから） | 中 |
| ⬜ | 猶予期間の締め（`DEFAULT_GRACE_UNTIL` = 2026-09-30）。締めると未登録端末が弾かれる | 低（期限あり） |
| ⬜ | 「退店」ボタンの確認文を平易に（「ログイン画面からも削除されます」→「ログインできなくなります」） | 低 |
| ⬜ | `index.html:10664` のPIN平文フォールバック（`||c.pin`）を削除。もう使われない | 低 |

## 5. 検討したが見送ったこと

**長いログインID＋PIN方式への切り替え**（端末登録を丸ごと廃止する案）。

業界調査の結果、Square・Toastは端末を登録するが**店の備品が数台だから成立**しており、
RESERVA・サロンボード等のサロン予約系は端末を登録しない。ShiftLinkは
**私物スマホに共有端末型の仕組みを当てている**ため、台数が人数を超えて増える構造だった。

ただし端末ペアリングは既に完成しており、乗り換えると同じ問題を別方式で解き直す二度手間になる。
まず既存を完成させ、それでも管理が煩わしければ改めて検討する、という判断。
