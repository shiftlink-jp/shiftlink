## 🚨 放置が一番危ない：9/30の自動発火は「営業中」に起きる

期限は **深夜0時ちょうど**。**KYOUKANOはその時間、営業中**（夜〜深夜2時頃）。
何もしなければ **9/29の夜、フロアが動いている最中に、誰も身構えていない状態で切り替わる**。

**期限は「それまでにやればいい日」ではなく「準備の有無に関係なく発火する日」。**
→ **こちらで時間を選び、営業時間外に先に締めること。** それが唯一の安全な進め方。

## ✅ 締めても大丈夫と言える根拠（D = 2026-08-01）

**2026-08-01以降にアプリを開いた端末は、すべてトークンを持っている。** 経路が2本あるため。

| 経路 | 対象 | 入ったコミット |
|---|---|---|
| サーバー側の自動登録（`pin-login:487-504`） | PINでログインした端末 | `bd1dd8c` / `8acf2ba`（2026-08-01） |
| `ensureDeviceTokenAfterLogin()` → `self_pair` | **生体認証だけの人**（`index.html:5161`） | `8acf2ba`（2026-08-01） |

⚠️ **`passkey` 関数は端末を自動登録しない**（`store_devices` へのINSERTが無く、読むだけ）。
生体認証だけを使う人にトークンが行き渡るのは、上記2本目の**アプリ側の `self_pair`** のおかげ。
**`index.html:5161` の `if(PIN_AUTH_MODE) setTimeout(ensureDeviceTokenAfterLogin, 1200)` を消すと、
生体認証ユーザーが締めた瞬間に全滅する。** 触らないこと。

### 残るリスクは2種類だけ
1. **2026-08-01以降に一度もアプリを開いていない人**（長期休み・復帰予定者）
2. **トークンを保存できない端末**（プライベートブラウズ、ストレージ制限）
   → この場合はログイン時に「この端末では登録情報を保存できません」とトーストが出る（`index.html:3611`）

## 🎚 締めるレバー：コードを触らずに切り替えられる

**本番に `PAIRING_GRACE_UNTIL` は登録されていない**（2026-08-07に `supabase secrets list` で確認）。
つまり今は `DEFAULT_GRACE_UNTIL`（2026-09-30）が効いている状態。

```bash
# 締める（過去日を入れる）
supabase secrets set PAIRING_GRACE_UNTIL="2026-08-07T00:00:00+09:00" --project-ref qgcgkrcrfzonmmygcdju

# 戻す（消すと猶予ONに倒れる＝fail-open）
supabase secrets unset PAIRING_GRACE_UNTIL --project-ref qgcgkrcrfzonmmygcdju
```

**これがコード編集より優れている理由**: 3ファイル書き換え＋再デプロイと違い、**数秒で元に戻せる**。
猶予は fail-open 設計（未設定・書式不正なら猶予ON）なので、消すだけで安全側に戻る。

⚠️ **シークレット変更が即時に効くかは未検証。** Edge Functionは起動時に環境変数を読むため、
反映が次のコールドスタートまで遅れる可能性がある。**締める当日に、実際に叩いて確認すること。**
