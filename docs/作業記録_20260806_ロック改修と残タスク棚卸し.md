# 作業記録 2026-08-06｜PINロックの改修（本番反映）と残タスクの棚卸し

きっかけ：「退店したセラピストがイタズラでPINをわざと間違えてロックをかけるのだけ阻止できればいい」
という今野さんの見立てから。調べたところ**その懸念は実在し、しかも無防備だった**ため対応した。

---

## 1. 結論（先に読むところ）

- **PINロックが店舗全体に広がらなくなった**（本番反映済み・実機でログイン確認済み）
- **同じ端末が間違え続けると、ロック時間が段々長くなるようになった**（15分→60分→24時間→登録解除）
- 残タスクを1件ずつ当たった結果、**Claudeだけで終わるものは無かった**。理由は本文3章
- **「オーナーの端末登録もリンク方式に統一する」という残タスクは、前提が間違っていた**ので取り下げ

---

## 2. やったこと（本番反映済み）

### ① PINロックの改修

**何が問題だったか。** これまでは「店舗全体の最終防衛線」として、登録済みの端末からでも
50回間違えると**店舗の全端末が60分ロック**される仕組みだった。
50回はスマホで**約2分**の作業なので、まだ端末登録が残っている退店者が、
その気になれば営業中の店を止められる状態だった。

**どう直したか。**

| | 以前 | いま |
|---|---|---|
| 登録済み端末で間違えたとき | 店舗全体のカウンタにも加算＝**巻き添え** | 自分の端末だけ。他の人に影響しない |
| ロック時間 | 常に15分 | 15分 → 60分 → 24時間（同じ端末が繰り返した場合） |
| それでも繰り返したら | ずっと15分ロックの往復 | **4回目でその端末の登録を解除** |

段階が上がったかどうかを数える期間は7日間。1週間おとなしくしていれば15分に戻る。

**未登録の端末からの攻撃には、店舗全体の防衛線を今までどおり残している**（10回・60分）。
ここを外すと、登録していない誰かが外から総当たりできてしまうため。

### ② 実装中に踏んだ罠（同じ改修をするとき必ず引っかかる）

ロック時間を24時間に延ばしたとき、**失敗回数を数える期間まで24時間に延びていた**。
これだと「1日かけて5回打ち間違えた」だけでロックに達する。受付の共有端末なら普通に起こる。
→ 「ロックする時間」と「数える期間」を別の設定に分離し、数える期間は常に15分に固定した。

### ③ 端末の自動登録（SaaS版のみ）

メールとパスワードでログインした端末を、自動で店舗に登録するようにした。
これが無いと、契約した本人が次回ログイン時に「店舗コードを入力してください」で行き止まりになる。

※**KYOUKANOには効かない**（PINモードのため）。KYOUKANOで端末が登録解除された場合の復旧は、
別の生きている端末から店舗コードを発行して登録し直す。全端末を失った場合の最終手段が、
紙で保管している8文字の緊急コード。

### ④ 確認したこと

- KYOUKANOで**実際にPINログインが通ることを確認**（今野さん実機）
- 段階カウンタの読み取り・ロック時間の決定・失敗回数の記録は、いずれも**PIN照合より前**を通るため、
  この1回の成功で「本番で実行された」ことが確定する
- データベース側の関数定義と、プログラムから渡している項目が一致することを突き合わせ確認
- **未確認**：実際にロックが発生したときの記録処理と端末の登録解除。
  5回連続で間違えないと通らない道のため、本番端末を15分止めてまでは試していない

## 3. 残タスクを1件ずつ当たった結果

「残りを終わらせて」という依頼に対し、**4件中3件は今野さんの操作が必要**で、
1件は**前提が間違っていた**ことが分かった。以下その内訳。

### ⛔ メール送信の設定 → 今野さんの操作が必要

**いまShiftLinkはメールを1通も送れない。** 設定が甘いのではなく構造的に送れない。
Supabaseの標準メール機能は「1時間2通」かつ**プロジェクトのメンバー以外には送信を拒否する**仕様のため、
お客さんのアドレスには最初から届かない。

いちばん怖いのは**オーナーがパスワードを忘れたとき**で、再設定メールが届かない＝
こちらから復旧する手段が無い。実店舗が増える前に必ず片付ける必要がある。

Claudeでは完了できない理由：Resendのアカウント作成・ドメインのDNS変更・Supabase管理画面への
入力は、いずれも本人操作でしか行えないため。

→ 所要40分で終わる手順書を用意した：[メール送信の設定手順_20260806.md](メール送信の設定手順_20260806.md)

### ⛔ Stripeのテスト契約の解約 → 今野さんの操作が必要

削除済みのテスト店舗「クライマックス」の契約（`sub_1U14lOI1tXgz7h5tBhxQ4AMJ`）が残っている。

Claudeでは実行できない。Stripeの鍵はSupabaseのSecretsに入っているが、
**登録済みの秘密は名前とハッシュ値しか読み出せない**（値は取り出せない設計）。
決済の鍵を別経路で探しに行くべきではないため、ここで止めた。

→ Stripeダッシュボード → Subscriptions → 該当契約 → Cancel subscription で30秒。

### ⚠️ 1オーナーが2店舗を持てない → 一部だけ対応、残りは要相談

**調べた結果、いま「2店舗目を作る導線が無い」だけで、コード上の締め出しが先に存在していた。**

`initSaasApp` が所属店舗を `.single()` で取っていた。この書き方は0件だけでなく
**2件以上でもエラー**になるため、所属が1件でも増えた瞬間にそのオーナーは丸ごとログイン不能になる。

→ 最も古い所属を選んで**必ず入れる**ように変更（staging）。
今の導線では2件目は作られないため実害は出ていないが、事故の芽を先に潰した。

**残り＝店舗の切替UI**。これは「どこに置くか」「切り替えたとき何が変わるか」の設計判断が要るので、
今野さんに相談してから作る。勝手に作ると作り直しになる。

### ❌ オーナーの端末登録もリンク方式に統一 → 前提が間違っていたので取り下げ

以前「8桁コードの手入力を無くしてリンク方式に統一する」と挙げていたが、**これは実装できない**。

コードを読むと、`inviteCast` に★付きの警告コメントで理由が書かれていた。
**リンクだけを送ると1人で2台登録されてしまう。**
iPhoneはSafariとホーム画面アプリでデータの保管場所が別なので、
リンクを開いた時点でSafariが1台目として登録され、ホーム画面に追加して開くともう一度登録が必要になる。

そのため現在は「先にホーム画面へ追加 → アイコンから開いてコードを入力」という手順にして、
登録を1回で終わらせている。**8桁コードは手抜きではなく、意図的な回避策だった。**

→ この残タスクは取り下げる。改善するなら「iPhoneの仕様をどう迂回するか」という別の課題になる。

### ⏭ 新規登録の通し確認（E2E）→ 意図的に見送り

本番で申し込みを通すと、本物のアカウント・店舗・Stripeのトライアルが作られる。
それを無人で消す作業まで発生するため、今野さんが見ている時にやるべきと判断した。
